# ТЗ: передача записей на встречу в Meta Pixel через Conversions API

Проект: психолог Кристина, лендинг https://lysakivska.com/trevoga/ → Telegram-бот → запись (сервер → Google Calendar).
Pixel (dataset) ID: `4350929461832601`. Рекламный кабинет: `act_2672992426390352`.

## Цель

Каждая реальная запись на диагностическую встречу должна приходить в Meta как серверное событие `Schedule`, привязанное к человеку, который пришёл с рекламы. Тогда Meta видит настоящие записи, а не только клики, и кампанию можно оптимизировать на них.

События:

| Событие | Когда | Откуда |
|---|---|---|
| `PageView` | открытие лендинга | браузерный пиксель (уже в коде) |
| `Lead` | клик по кнопке «в Telegram» | браузер (`fbq`) + сервер с тем же `event_id` (дедупликация) |
| `Schedule` | запись создана на сервере / в календаре | только сервер (CAPI) |

## Проблема и решение

Telegram-бот не браузер: в нём нет cookie `_fbp`/`_fbc` и fbclid. Поэтому данные клика нужно сохранить на лендинге и передать в бот через deep-link параметр `start`.

### Шаг 1. Лендинг: сохранить данные клика

1. При открытии страницы пиксель сам ставит cookie `_fbp`. Если в URL есть `fbclid`, а cookie `_fbc` нет, создать её: `fb.1.<timestamp_ms>.<fbclid>` (срок 90 дней).
2. На клик по кнопке Telegram:
   - сгенерировать `sid`: случайная строка 16-32 символа, только `A-Za-z0-9_-` (лимит Telegram на `start` = 64 символа, только эти символы);
   - `event_id = "lead_" + sid`;
   - вызвать `fbq('track', 'Lead', {}, {eventID: event_id})`;
   - отправить на сервер `POST /api/fb-click` (через `navigator.sendBeacon`, чтобы не задерживать переход): `{sid, fbp, fbc, event_source_url: location.href, utm_*: ...}`. IP и User-Agent сервер берёт из самого запроса;
   - перейти на `https://t.me/<bot>?start=<sid>`.
3. Сервер сохраняет запись `clicks(sid, fbp, fbc, client_ip, user_agent, event_source_url, utm, created_at)`, хранить 90 дней.
4. (Желательно) Сервер сразу отправляет CAPI `Lead` с `event_id = "lead_" + sid`, чтобы событие дошло даже при блокировщике рекламы. Meta склеит его с браузерным по `event_id` + `event_name`.

### Шаг 2. Бот: связать Telegram-пользователя с кликом

- В обработчике `/start <sid>` сохранить связь `tg_user_id ↔ sid` (если пользователь уже был, обновить на последний sid).
- Если пользователь пришёл без `sid` (органика), событие `Schedule` всё равно можно отправлять, но без fbc/fbp оно хуже матчится.

### Шаг 3. Запись: отправить `Schedule`

В месте кода, где создаётся событие в Google Calendar (после успешного создания), отправить:

```
POST https://graph.facebook.com/v21.0/4350929461832601/events?access_token=<TOKEN>
Content-Type: application/json

{
  "data": [{
    "event_name": "Schedule",
    "event_time": <unix seconds, момент записи>,
    "event_id": "schedule_<booking_id>",
    "action_source": "website",
    "event_source_url": "<event_source_url из clicks>",
    "user_data": {
      "fbc": "<из clicks>",
      "fbp": "<из clicks>",
      "client_ip_address": "<из clicks>",
      "client_user_agent": "<из clicks>",
      "external_id": ["<sha256(tg_user_id)>"],
      "em": ["<sha256(lower(trim(email)))>"],
      "ph": ["<sha256(только цифры, с кодом страны)>"],
      "fn": ["<sha256(lower(имя))>"]
    },
    "custom_data": {
      "content_name": "diagnostic_session",
      "value": 0,
      "currency": "USD"
    }
  }]
  // для проверки добавить на верхний уровень: "test_event_code": "TESTxxxx"
}
```

Правила:
- `em`, `ph`, `fn`, `external_id` хешировать SHA-256 (hex, lowercase) после нормализации. `fbc`, `fbp`, IP, User-Agent НЕ хешировать.
- Передавать только те поля, которые есть. Пустые не слать.
- `event_time` не старше 7 дней.
- Ошибки CAPI логировать и ретраить (до 3 раз), запись клиента от этого не должна ломаться.
- Отправка асинхронная, не блокирует ответ бота.
- Отмена записи: событие не отзывается, ничего не отправлять.
- Версию Graph API брать актуальную (v21.0 или новее).

## Токен доступа

Events Manager → датасет «Тестовый пиксель» (4350929461832601) → Настройки → Conversions API → «Создать маркер доступа». Хранить в переменной окружения сервера (например `META_CAPI_TOKEN`), не коммитить в репозиторий.

## Проверка

1. Events Manager → датасет → «Тестовые события» → скопировать код `TESTxxxx`.
2. Временно добавить `test_event_code` в запросы.
3. Пройти путь: открыть лендинг с `?fbclid=test123` → клик → `/start` в боте → записаться.
4. В «Тестовых событиях» должны появиться: `PageView` (браузер), `Lead` (браузер + сервер, помечено «Дедуплицировано»), `Schedule` (сервер) с параметрами fbc/fbp.
5. Убрать `test_event_code`. Через 24-48 часов проверить Event Match Quality для `Schedule` (цель ≥ 6/10).

## Приёмка

- [ ] Cookie `_fbc` ставится при наличии fbclid
- [ ] Клик → `sid` в deep-link, данные клика сохраняются на сервере
- [ ] `/start sid` связывает tg_user_id и клик
- [ ] Каждая новая запись даёт ровно одно событие `Schedule` с уникальным `event_id`
- [ ] Браузерный и серверный `Lead` дедуплицируются
- [ ] Токен в env, не в коде
- [ ] Тестовые события видны в Events Manager
